## 🛠️ Context & Mission
* **Primary Objective**: Ingesting high volumes of YouTube video transcriptions to build a clean, searchable knowledge base, then repurposing that data into high-engagement blogs and podcast scripts.
* **Core Philosophy**: Absolute fidelity to the reference material. Never lose the original speaker's core insights, unique case studies, or data points during summarisation or adaptation.

## 📝 1. Transcript Summarisation Rules (Knowledge Base Building)
When processing a raw video transcription, always output the summary using this exact structure:
* **The Hook & Core Thesis**: 1–2 sentences max detailing the absolute main takeaway.
* **Key Arguments Checklist**: A bulleted list of the main points made, ordered by importance (not chronology).
* **High-Yield Assets**: Extract every specific statistic, book recommendation, software tool mentioned, or framework name. **Never** generalise these (e.g., write "Prisma ORM", not "a database tool").
* **Case Studies/Anecdotes**: Summarise any real-world stories or personal examples used by the speaker. These are vital for humanising future blogs and podcasts.
* **The "So What?" Factor**: Why does this video matter? What is the actionable advice?

## ✍️ 2. Blog Post Generation Standards
* **No AI Fluff**: Immediately ban words like *delve, leverage, robust, seamless, testament, unlock, dive into, landscape, in today's fast-paced world, at the end of the day*.
* **Formatting for Skimmers**: Use frequent, bold Markdown headers (`###`), short sentences (under 15 words where possible), and punchy, single-fragment bullet points.
* **Tone**: Authoritative, engaging, and clear. Write at an intermediate level so it remains accessible to a global audience, avoiding unnecessary academic jargon.
* **Structure**: Lead with the most shocking or valuable insight first (Inverted Pyramid style). Every section must end with a transition sentence that pulls the reader to the next.

## 🎙️ 3. Podcast Scripting Standards
* **Conversational Rhythm**: Write text explicitly designed to be spoken aloud. Use contractions (*don't, you're, it's*), short pauses (represented by ellipses `...` or em-dashes `—`), and varied sentence lengths.
* **Engagement Markers**: Build in natural rhetorical questions, verbal signposts (e.g., *"Now, here is where it gets interesting..."*), and summary recaps.
* **Audio-Friendly Formatting**: Bold names of speakers or sound cues (`[Sound Effect: Brief transitions music]`). Keep paragraphs short so the host can breathe naturally.

## ⬇️ 4. YouTube Download Workflow (Source Acquisition)
Source audio is fetched via the `youtube-video-downloader` skill, which reads a JSON array of playlist URLs (default `video-injest/video.json` — note the intentional "injest" spelling of the folder) and downloads into `video-injest/download-video/`.
* **One Resilient Pass**: Run `yt-dlp` directly against each playlist URL — yt-dlp expands the playlist itself. Do **not** use the old two-step "enumerate URLs, then download each with `--no-playlist`" flow; it is redundant.
* **Standard Flags**: `--extract-audio --audio-format mp3 --audio-quality 0 --write-info-json --write-thumbnail --convert-thumbnails jpg --output "video-injest/download-video/%(title)s/%(title)s.%(ext)s"`.
* **No Stray Playlist Folder**: Always pass `--no-write-playlist-metafiles`. Without it, yt-dlp writes the playlist's own metadata as an extra folder named after the playlist title (e.g. `aa/` holding `aa.info.json` + `aa.jpg`, whose `id` equals the playlist ID). That folder is **not** a failed video — it is playlist-level metadata, and the flag suppresses it.
* **Batch Safety**: For multi-video runs add `--ignore-errors --no-overwrites` so one bad/region-locked video doesn't abort the batch and re-runs skip already-completed files.
* **Output Layout**: Each video gets its own folder containing exactly three files — `<Title>.mp3`, `<Title>.info.json`, `<Title>.jpg`. Report the count of successful downloads versus expected when done.

## 📚 5. Ark Knowledge Base (Obsidian Vault)
The processed knowledge base lives in an Obsidian vault named **Ark**, located at `Ark/` in the repo root. This is the destination for the finished, repurposed output — the clean, searchable library the whole pipeline feeds.
* **Role in the Pipeline**: `video-injest/download-video/` holds raw source artifacts (`.mp3`, `.info.json`, `.srt`, `.meta.json`). **Ark** holds the *curated* output: video summaries (Section 1), blog drafts (Section 2), and podcast scripts (Section 3). Keep raw acquisition out of Ark.
* **It Is a Real Obsidian Vault**: `Ark/.obsidian/` contains the app's config (tracked in git). Treat notes as Obsidian Markdown — use `[[wiki-links]]` to connect related videos, ideas, and people so the graph stays navigable.
* **Quote titles containing a colon (or other YAML-special chars).** `prepare-note.sh` emits the title verbatim, so a title like `IBS vs Bowel Cancer: How to Tell the Difference` or `Iron vs. Steamer: Which is Best…?` comes out **unquoted** — which is invalid YAML (the `:` starts a mapping). Wrap any such `title:` value in double quotes before writing the note. (Hit on 3 notes in the 19-07-2026 run.)
* **Note Format**: One Markdown note per video. Lead with YAML frontmatter mapping the `<Title>.meta.json` fields, then a `![[<videoId>.jpg]]` thumbnail embed, then the structured summary body. The frontmatter mapping is exact:

  | Frontmatter key | Source (`<Title>.meta.json`) | Notes |
  | --- | --- | --- |
  | `title` | `title` | — |
  | `topic` | `category` | YAML list (one `- <category>` item) |
  | `channel` | `channel` | — |
  | `origin link` | `origin` | full YouTube URL |
  | `publish date` | `published date` | `YYYY-MM-DD` |
  | `watch date` | `watch date` | `YYYY-MM-DD` |

* **`topic` Is Inferred, Not Copied**: `extract-video-meta` writes the `topic`/`category` field as the literal sentinel `__INFER__` (YouTube's own category is useless). Replace it by **inferring from the categories already in use** in `Ark/Learning`. Don't trust a stale hard-coded list — **derive the live set at run time**: `grep -rhA1 '^topic:' Ark/Learning | grep -E '^\s*-' | sed 's/^[[:space:]]*-[[:space:]]*//' | sort | uniq -c | sort -rn`. As of 01-07-2026 the set is: **Investment, Habit, Health, Charisma, Style, Business, Home, Procrastination, Politics, Geopolitics** (Business + Home were coined during the 01-07-2026 run — Business for company/business-model breakdowns, Home for house/interior-design content). **Reuse an existing label before coining a new one**, and note that `Procrastination` is the home for productivity / getting-unstuck / deep-work content (not `Habit`). If nothing genuinely fits and you must coin a new label, **flag it in your summary and confirm with me** rather than silently proliferating categories. *(The 45-video 19-07-2026 run reused the existing set with no new coinage: Style 17, Investment 11, Charisma 8, Health 5, plus one each of Business, Home, Habit. Useful precedents: a biography/tycoon profile with a heavy style component → **Business** (the through-line was business lessons); a "habits of an elegant man" lifestyle piece spanning grooming/wardrobe/manners → **Habit**; social-skills / dating / etiquette / persuasion breakdowns → **Charisma**.)*
* **Note Location & Naming**: `Ark/Learning/<MM>/<DD-MM-YYYY>-<N>.md`, all derived from the **watch date**. `<MM>` is the 2-digit month folder; the filename is the watch date as `DD-MM-YYYY` plus `-<N>`, where `N` is the next free sequence number for that date (three videos watched 19-06-2026 → `19-06-2026-1.md`, `-2.md`, `-3.md`).
* **Thumbnails**: Copy each video's `<Title>.jpg` into `Ark/Misc/Thnmbnails/<videoId>.jpg` and embed it as `![[<videoId>.jpg]]`. `<videoId>` is the `v=` value of the `origin` URL (also `id` in `.info.json`). The folder spelling **"Thnmbnails"** is intentional (legacy) — keep using it; do not create a second `Thumbnails/` folder. Obsidian resolves `![[file.jpg]]` by filename, so the embed works regardless of folder.
* **The `build-ark-note` Skill**: The final pipeline stage is automated by the `build-ark-note` skill (`.claude/skills/build-ark-note/`). It runs after `transcribe-audio` and `extract-video-meta`: for each `video-injest/download-video/<Title>/` folder it copies the thumbnail, computes the note path/frontmatter (`scripts/prepare-note.sh` handles the mechanical parts), authors the summary body from the `.srt`, writes the note, then **deletes the source folder** so `video-injest/download-video/` only ever holds unprocessed work. Trigger it with phrases like "build the Ark notes" or "add this video to Ark".
* **Leave the Stock Note Alone Unless Asked**: The vault currently holds only Obsidian's default `Welcome.md`. Do not delete or overwrite it unless I ask.

## ♻️ 7. Re-run Safety & Pipeline Gotchas
Hard-won operational lessons for the `process-video` pipeline. The build stage deletes the source folder, so re-runs are normal and these prevent duplicate/wrong output.
* **Dedup BEFORE authoring — the pipeline has none.** `prepare-note.sh` does **no** dedup, and `watch date` = the day the run executes. Because build deletes the folder when done, a re-run will happily **re-download a video still in the playlist and write a second, fresh-dated note**. So after download, for each `<Title>/` grep its `.info.json` `id` against `Ark/Learning` (`grep -rl "<id>" Ark/Learning`). If it already exists, **skip it: delete the folder without authoring**, and leave the existing note untouched. Confirm the dedup policy with me if a match is found (e.g. skip vs. replace).
* **The `id` is the source of truth, not the title.** `yt-dlp --flat-playlist` titles can be **stale** — a creator may have retitled a video, so the flat-list title won't match the downloaded `<Title>` folder. Always identify, dedup, and match videos by the `id` field in `.info.json` (= the `v=` param / `<videoId>`), never by title string.
* **whisper is slow and runs in the foreground.** `transcribe.sh` calls whisper in the foreground (minutes per video). Launch it via the harness's own background mechanism (no trailing `&`) so completion is actually tracked — a wrapper that returns instantly with a trailing `&` gives a **misleading "completed" signal** while whisper is still running. Alternatively, wait until the `.srt` file appears before proceeding.
* **Pipeline the per-video loop.** Transcription dominates wall-clock time. While authoring the current video's note, kick off the **next** video's `transcribe.sh` in the background (and run `extract-meta.sh`, which only needs the `.info.json`, immediately). Don't serialize.
* **`prepare-note.sh` already copies the thumbnail** into `Ark/Misc/Thnmbnails/<videoId>.jpg` — no manual copy step needed; just verify it landed.
* **Compilations & podcasts.** Some "videos" are multi-guest compilations or interviews. Center the note on the **titular** segment but capture the rest faithfully. **Omit sponsor ad-reads** (e.g. supplement/product spots) from High-Yield Assets — they are ads, not the speaker's content.
* **Omit the creator's own funnel/CTA too.** Beyond third-party sponsors, drop the self-promo that ends most videos — "join my mentorship / community," "click for my free training," "check out [my program]," subscribe/like begging (e.g. Founder OS, "work with me," school.com/RMRS). But **keep a genuine, non-sponsored tool/book/product recommendation** even when it links out — if the speaker explicitly says "this isn't sponsored" and it's real advice (e.g. **Monarch Money**, **Opal**), it belongs in High-Yield Assets.
* **Title vs. delivered framing can invert.** The title may be click-bait that's the opposite of the actual content (e.g. "5 *low-status* habits" delivered as "5 traits of *high-status* communicators," counted down). Author from what's actually said, and note the discrepancy neutrally. Likewise, a "25 X" listicle may only spell out 24 — capture what's there and flag the gap inline rather than inventing the missing item. **Title numbers are frequently wrong — count what's actually delivered and flag the mismatch neutrally.** Seen in the 19-07-2026 run: "11 Science-Backed Habits" delivered **12**; "Send Her These 7 Texts" delivered **5 tips + 2 bonus rules**; "20 Things Men Should Never Wear" specified only **19** (the 20th left to the comments); "How Do You Hang?" promised the answer but ended on **5 unproven theories**.
* **Some videos have very long transcripts.** Long-form guides (e.g. a ~52-minute "ultimate investing guide", a ~45-minute doctor explainer) produce `.srt` files that exceed one `Read` window — page through with `offset`/`limit` (or `Grep` for a section) and author from the **whole** transcript, never from the first page alone.
* **The playlist is a rolling, curated queue that changes wholesale between runs.** Don't assume it's append-only: the same `list=` URL had 3 videos, then those were swapped for 2 others, then swapped again for 47 within a single day. This is exactly why dedup-by-`id` (above) is mandatory every run, and why "nothing new to do" is a legitimate outcome (all playlist items already have notes).

## 📰 8. Blog Factory (Ark Notes → Published Blog)
The `blog-factory/` folder is the second repurposing stage: it turns a curated batch of finished Ark notes into a single blog post. This is downstream of the whole `process-video` pipeline — it consumes the clean Section-1 summaries, it does **not** touch raw `video-injest/download-video/` artifacts. Automated by the **`produce-blog` skill** (`.claude/skills/produce-blog/`); invoke it with **two required parameters**, a blog profile and a CSV: `/produce-blog <profile> <csv>` (e.g. `/produce-blog s1 health-batch.csv`). If a request ("produce a blog", "run the blog factory", pointing at a `.csv` in `blog-factory/`) doesn't name both, stop and ask for the missing one rather than assuming a default.
* **Blog profiles define *how* a post gets written** — stance, research approach, register, structure, precision rules, output naming — and live at `.claude/skills/produce-blog/profiles/<name>.md`. **`s1`** (`profiles/s1.md`) is the original/default behavior described in the rest of this section: own-the-ideas stance, independent research, three-part macro structure, 3,000-word cap. **`s2`** (`profiles/s2.md`) is a lighter ~75%-rigor variant: same stance and structure, but research scoped to only the 2–4 headline claims, more forgiving sourcing, and a shorter 1,200–1,800 word target. **`s3`** (`profiles/s3.md`) is a minimal ~50%-rigor variant: no independent research at all, softspoken/low-key tone, bullet-heavy, everyday vocabulary, no macro-structure requirement, under 800 words. New profiles can vary any of that; the bullets below describe `s1` specifically.
* **The manifest is a CSV, header `name,topic,title`.** Each row's `name` is an Ark note basename in `DD-MM-YYYY-N` form; `topic` is the Ark category; `title` is the original video title (context only — **the note is the source of truth**, not the title). One CSV = one blog, named explicitly as the skill's second parameter.
* **The `<csv>` parameter can name a *folder* of one-row CSVs — that means one post per file, not one post per folder.** Established in the 09-08-2026 run: `Investment.csv` (40 rows) was first split into 40 one-row manifests at `blog-factory/Investment/<name>.csv` (one file per Ark note, header preserved, titles containing commas re-quoted). The follow-up `/produce-blog s3 Investmemt` then matched no single `.csv` — the name (typo included) resolved to that **directory**. The right read is *N independent single-row manifests → N independent posts*, but **confirm it before writing 40 files**. Splitting a manifest this way is a legitimate workflow: it turns one synthesized batch post into a set of focused single-source posts.
* **The same manifest folder can be re-run under a different profile, and that's a legitimate request.** The 40 Investment manifests were published once at `s3` (09-08-2026) and again at `s2` (10-08-2026). Because published posts get moved out of `output/`, an **empty `output/` is not evidence the folder is unprocessed** — check `Archive/` and ask before assuming a re-run is a mistake. The practical constraint is that both sets go live: **author the second pass from the notes afresh rather than expanding the first pass**, so titles and angles separate naturally instead of reading as near-duplicates of already-published posts.
* **Args matching `produce-blog`'s signature mean the whole chain, even when typed at another skill.** `/blog-ncw-adapter s2 Investment` (10-08-2026) named a profile and a manifest folder, which the adapter has no use for — the intent was *produce 40 posts, then adapt them*. Two readings existed (produce-only vs produce-and-adapt), and 40 files is too expensive to guess at, so **ask which, then run the chain**. Same rule as the folder-means-batch convention: read the arguments, not just the skill name.
* **Splitting a batch CSV into one-row manifests is a recurring request — use the `csv` module, never shell text-slicing.** Done three times (Investment 40, Health 25, Charisma 25). Titles routinely contain commas and are already quoted, and at least one row per batch has been CJK, so `cut`/`awk` will corrupt output that `csv.reader`/`csv.writer` round-trips correctly. The procedure: read with `csv.reader` capturing the header separately, skip blank rows, **abort on any duplicate `name`** (two rows would collide on one output filename and silently lose data), then write `blog-factory/<Topic>/<name>.csv` with header + that single row, all I/O at `encoding='utf-8'`. Leave the source CSV untouched. Verify by round-trip rather than eyeball — `sorted(reassembled) == sorted(original)` — plus checking each filename matches its `name` field.
* **Resolving a row to its note:** `name` → `Ark/Learning/<MM>/<name>.md`, where `<MM>` is the month segment of the `DD-MM-YYYY` date (e.g. `12-05-2026-5` → `Ark/Learning/05/12-05-2026-5.md`). Resolve **every** row before writing. If a note is missing, report the gap and continue with what exists — never invent content for a missing row. **Pre-flight the whole batch with a shell loop** before authoring anything — deriving `<MM>` with `cut -d'-' -f2` and testing `-f` on each path catches every miss in one pass instead of 40 interruptions.
* **A CSV's rows can run together if a newline is missing mid-file.** Hit in the 02-08-2026 run: `Charisma2.csv` had no line break between row 2's `title` and row 3's `name`, so the file only *looked* like 2 data lines for 3 intended rows (`...Enjoy15-05-2026-3,Charisma,...`). The tell is a `title` field that runs straight into something matching `DD-MM-YYYY-N,<topic>,` — split there rather than treating it as a missing row, and confirm the split by checking both derived note paths actually exist before proceeding.
* **The pipeline doesn't dedup notes across separate blog runs.** Each CSV is its own independent request — nothing stops the same Ark note from anchoring one CSV's post and also appearing inside a different CSV's batch. Hit in the 02-08-2026 run: `15-05-2026-3` (Tommy Shelby) was the sole row in `Charisma3.csv` after already being used alongside two other notes in `Charisma2.csv`. Not an error — just flag it in the sign-off so I know the same source now backs two published posts.
* **A single-row CSV is a valid manifest.** `Charisma3.csv` (02-08-2026 run) had exactly one row. There's no batch to synthesize across — just condense that one note's own core view and argue it, same own-the-ideas rule as any other batch.
* **Different Ark notes can point at the *same* video — check `origin link`, not the note name.** The Section-7 dedup rule protects the *vault*; nothing protects a blog batch. Across the whole 40-manifest Investment folder the true figure is **40 notes covering 34 distinct videos** — 11 notes sit in 5 duplicate groups, so 6 are excess. (The 09-08-2026 run first recorded this as "9 notes covering 4 distinct videos", which undercounts; the 10-08-2026 re-run verified 34 with the one-liner below.) The groups: `19-06-2026-1` / `19-06-2026-7` / `22-06-2026-2` are all the same ETF video (`VzjqfYEmxZ0`), plus pairs at `21-06-2026-3`/`-4`, `19-06-2026-9`/`23-06-2026-10`, `19-06-2026-3`/`22-06-2026-3`, and `21-06-2026-1`/`29-06-2026-20`. **Derive it, don't trust the number written here** — strip the `&t=` suffix or `757B7EjOvDM&t=7s` counts as its own video:

  ```bash
  for f in blog-factory/<folder>/*.csv; do n=$(basename "$f" .csv); mm=$(echo "$n" | cut -d'-' -f2);
    grep -m1 '^origin link:' "Ark/Learning/$mm/$n.md" | sed 's/.*v=//; s/&.*//'; done | sort | uniq -c | sort -rn
  ```
 These are re-downloads from before dedup was enforced, and the summaries differ in emphasis even when the source is identical. **Grep the frontmatter `origin link` across the batch before authoring**, then either give each note its own angle (what the 09-08-2026 run did — each post was built from its own note's actual emphasis, so the ETF trio became "five numbers to check", "the one number most people skip", and "not as diversified as you think") or fold them into one post. Either way, **flag the duplication in the sign-off** so the count of posts vs. count of real sources is visible before publishing.
* **⭐ Own the ideas — do NOT retell or critique the source videos.** This is the single most important rule and the one I got wrong first. The blog is **my own authoritative piece built on the digested views**, not a recap of what the creators said. Concretely: digest all the notes, condense them to their **core view/thesis**, then argue that thesis in my own voice. **No** "Dr. Alex says…", "the video claims…", "the creator argues…" — strip all narration of the sources. The creators are the *seed* of the idea, not the *subject* of the blog. (The first Health draft failed by attributing everything and retelling each video; the accepted redo owned the argument outright.)
* **Do independent research and bring my own supporting material.** For this stage I **override** the vault's "no outside claims" rule (that rule governs Ark notes, not blogs). Use `WebSearch`/`WebFetch` to find real studies, data, and examples that back the thesis, and **cite them inline as markdown links** plus a "Sources & further reading" list at the end. Prefer primary/authoritative sources (journals, PubMed/PMC, major bodies). Where my research **refines a number from the notes**, trust the researched figure and use it (e.g. notes said glycine "~10g"; trials use **3g** → the blog says 3g).
* **Keep specifics specific, but they're now mine to state.** Every dose, stat, mechanism, tool, and framework name stays exact ("magnesium glycinate, 200–400mg *elemental*", never "a magnesium supplement") — the difference from the notes is that I now assert them as researched fact with a citation, not as "the speaker's claim." Preserve honest hedges (a "modest, consistent" effect is not "proven"). Surface genuine conflicts in the evidence as content.
* **Find the synthesis angle; avoid "N tips from N videos."** Read all notes fully, then build one cohesive argument around the claim the batch collectively points to but no single video states outright. The formula that keeps working: **name the single upstream variable the whole batch shares, then argue every technique is downstream of it** (Health: insulin resistance is the silent throughline, and cheap daily movement beats the supplement economy; Charisma: charisma isn't performance, it's the absence of need — "want it, don't need it" — and humor/small-talk/listening/gravitas techniques are all symptoms of that state; Habit: discipline isn't willpower, it's identity backed by evidence — every technique is a way to manufacture proof you keep promises to yourself; Sleep/Health — magnesium + heart-disease + sleep-tea batch, 02-08-2026 — sleep *depth and continuity*, not hours logged, is the nightly cardiovascular repair mechanism, and magnesium plus bedtime ritual-stacking (chamomile, glycine, magnesium glycinate) are both just deliberate attempts to engineer that deep-sleep state rather than separate wellness trends). **When the batch disagrees internally, that tension IS the angle** (Habit: the Jim Rohn-style "stop negotiating with yourself" grind talks vs the identity/mindset videos) — treat the folk model as the foil the research complicates, and let the disagreement drive the argument. That tension doesn't have to sit inside one CSV either: in the 02-08-2026 run it arrived as two separate manifests (`Habit2.csv` = the grind-talk pair, `Habit.csv` = the identity/self-love pair), each becoming its own post — the split is fine as long as each post's own synthesis still holds together internally.
* **Three-part macro structure — say it three times.** Section 1: a high-level **executive view** at the very beginning of the blog, straight after the frontmatter — *say what you're going to say*. Section 2: the **main body** — *say it*. Section 3: a **summary** recap holding the "so what" actions — *say what you have said*. The "Sources & further reading" list follows the summary and must list **every reference used** during research, not just those cited inline.
* **Match register to the topic.** Base rules are the Section-2 Blog Post Standards (banned AI-fluff words, skimmer `###` headers, short sentences, inverted pyramid, transition sentences). Layer topic judgment on top: **Health/medical** = evidence-first, cite research, keep every dose/stat/mechanism exact and safety caveats intact. **Investment/Business** = names, figures, framework names verbatim; flag speculation as opinion. **Style/Charisma/self-improvement** = personal, second-person, example-driven.
* **Examples earn their keep.** Illustrative scenarios and analogies (key-and-lock for insulin, muscles' insulin-free "back door") are good for clarity — but a factual claim (a statistic, dose, study result) needs a real cited source, not a vibe.
* **Research workflow that works: one search per core claim, batched in parallel.** Before writing, list the claims the argument leans on and run ~6–8 targeted `WebSearch` calls (in parallel batches of 2–3) to pin each to its **canonical study** — the named paper behind the technique (e.g. spotlight effect → Gilovich 2000; question-asking → Huang 2017; "chunky questions" → Aron 1997's 36-questions; listening → Itzchakov & Kluger; humor → McGraw & Warren's benign violation theory; vocal pitch → Klofstad 2012). Cite the journal/PDF link when reachable; a reputable secondary summary (e.g. BPS Research Digest) is acceptable when the paper is paywalled. Author names + year + journal in the "Sources & further reading" entries. **Failed replications are content, not obstacles**: the search for a canonical study often surfaces its famous null (ego depletion → Hagger et al. 2016's 23-lab replication; Bryan 2011 "being a voter" → Gerber et al. 2016 field null) — cite both and hedge honestly; the conflict strengthens the piece's authority rather than weakening the claim.
* **Banned words stay banned even when a note uses one legitimately.** The Tommy Shelby note's "carrot and stick *leverage*" is a real concept, but "leverage" is on the Section-2 ban list — substitute a precise alternative ("options", "walk-away power", "bargaining position") rather than importing the banned word. **Investment/finance topics make this trap much worse**, because "leverage" there is the correct technical term for a real thing and slides in unnoticed. Confirmed substitutions from the 09-08-2026 run: real-estate down-payment leverage → **"borrowed money"**; options as leveraged exposure → **"borrowed exposure"**. Others that work: "borrowing against", "amplified exposure", "gearing".
* **Always run the banned-word and source-narration greps before signing off** — self-review by re-reading 40 posts doesn't scale, and both slips are mechanical enough to catch with two commands. The `leverage` pair above was caught this way, not by reading:

  ```bash
  grep -rioE '\b(delve|leverage|leverages|leveraging|robust|seamless|testament|unlock|unlocks|unlocking|dive into|diving into|landscape)\b' blog-factory/output/*/index.md
  grep -rinE 'the video (says|claims|argues)|the creator|the speaker|the host (says|argues)|in the video' blog-factory/output/*/index.md
  ```

  Empty output from both = clean. The second one guards the ⭐ own-the-ideas rule, which is the single easiest thing to backslide on across a long batch.

  **The banned-word grep produces false positives once you cite sources** (10-08-2026 run). URLs and real article titles contain the banned words — `graniteshares.com/research/understanding-the-decay-risk-in-leveraged-etfs/`, the publisher *Leverage Shares* — and no amount of rewriting your prose clears them. Strip URLs before grepping so you're only checking your own writing:

  ```bash
  for f in blog-factory/output/*/index.md; do
    sed -E 's#https?://[^)]*##g' "$f" \
      | grep -ioE '\b(delve|leverage|leverages|leveraged|leveraging|robust|seamless|testament|unlock|unlocks|unlocking|dive into|diving into|landscape)\b' \
      | sed "s#^#$(basename $(dirname $f)): #"
  done
  ```

  Residual hits after that are in **link text**, and the fix is to describe the source rather than quote its title verbatim ("GraniteShares research on decay risk in geared ETFs"). Don't alter the URL, and don't leave a banned word in prose just because a citation nearby has one.
* **Self-improvement register, confirmed shape:** second person throughout, research citations woven into an opinionated argument (not an evidence review), and close the "so what" as a **numbered drill list** of small concrete reps ("give someone 10 minutes of full attention", "swap one *what* for one *why* per conversation"). The drills should map back to the sections, one each.
* **The Charisma throughline keeps resurfacing in variations — don't force-fit the last angle onto a new batch.** "Want it, don't need it" (absence of need) and "stop performing, just pay attention" (presence over performing) are two distinct confirmed angles from two different Charisma batches (02-08-2026 run) — both are true of the topic in general, but each specific batch of notes points more naturally at one or the other. Read the batch first and let it tell you which.
* **s3 profile, confirmed shape (02-08-2026 run, 4 posts across Habit and Charisma):** dropping independent research doesn't mean dropping the synthesis-angle step — the same "name the shared throughline, or the internal tension" work from s1 still applies, just stated plainly and without citations (e.g. "discipline isn't willpower, it's identity" as self-love vs. discomfort-training; "want it, don't need it" as the read on Ryan Gosling/Ryan Reynolds humor techniques). A quiet-voiced, bullet-heavy post built on a real angle beats a flat "N tips from N videos" listicle even at 50% rigor. Each post closed with a short, un-numbered "a few small things to try" list rather than s1's numbered drill list — keep that lighter touch for s3.
* **s3 at scale, confirmed (09-08-2026 run, 40 single-source Investment posts):** the profile holds up across a large batch, and the per-post shape settles at **~380–510 words** (mean ~440) — comfortably under the 800 cap without padding. Working method that made 40 tractable: **read 5 notes in one parallel batch, write those 5 posts in one parallel batch, repeat.** Don't read all 40 up front (context) and don't go one at a time (slow). Two s3-specific things this run confirmed:
  * **A single-source post needs an *angle*, not a summary.** With no batch to synthesize across, the move is to find the one claim the note is really making and lead with it — "the fee is the only number guaranteed to cost you", "waiting for a dip is still market timing", "one nice thing costs more than one nice thing". A note that's structurally a listicle (7 mistakes, 8 investments) still needs a sentence naming what the list has in common; the 7-worst-purchases note became "every expensive mistake shares the same shape — manufactured urgency", which is nowhere in the note but is what the note is about.
  * **Titles must differentiate themselves when sources overlap.** With duplicate-video notes in the batch (see the dedup bullet above), near-identical titles are the visible failure mode. Author each from its own note's actual emphasis and the titles separate naturally.
* **s2 at scale, confirmed (10-08-2026 run, the same 40 single-source Investment manifests, re-run under `s2`):** the profile holds, but the per-post shape settles at **~920–1,330 words (mean ~1,080)** — *below* s2's stated 1,200–1,800 target. That band appears calibrated for multi-note batches; a single note simply doesn't support 1,500 words without padding. **Treat the miss as correct behaviour** (s2 says "no minimum: say what the argument supports and stop") and flag it in the sign-off rather than inflating. Same 5-and-5 working method as s3, with a research step inserted: **read 5 notes in parallel → one batch of ~6 parallel `WebSearch` calls covering that batch's headline claims → write those 5 posts in parallel → repeat.** Eight rounds for 40 posts. Sources reuse heavily across posts in one domain (the S&P 500 long-run return, the Morningstar gap, the SPIVA scorecard, the credit-card APR figure all recurred), so later batches need fewer searches than earlier ones.
* **s1 at scale, confirmed (10-08-2026 run, 25 single-source Health manifests):** the full-rigor profile works fine on single-source manifests, and the per-post shape settles at **~1,010–1,350 words (mean ~1,180)** — well under the 3,000 cap, because one note plus its research simply doesn't support more without padding. Same 5-and-5 method as s2 with a heavier research step: **read 5 notes in parallel → 3 parallel `WebSearch` calls, then 3 more, aimed at that batch's canonical studies → write those 5 posts in parallel → repeat.** Five rounds for 25. Medical sources reuse heavily across a batch (GLUT4/insulin-independent glucose uptake, the nocturnal blood-pressure dip, and the post-meal walking trial each recurred in 3+ posts), so later rounds need noticeably fewer searches.
* **⭐ At s1 on health topics, expect research to contradict the notes several times per batch — that's the profile working, not a problem.** It fired **six times in 25 posts** on the 10-08-2026 Health run, and in every case the corrected version made a better paragraph than the original claim would have:
  * *"Your blood pressure problem isn't salt"* overcorrects — the Cochrane review (He/Li/MacGregor 2013) finds a sustained 4.4g/day cut lowers systolic ~**4.18 mmHg**. The defensible thesis is that salt works *modestly* and insulin-driven sodium retention is the untouched lever.
  * *Glycine "5–10g"* for sleep → trials use **3g** (Yamadera 2007). Exactly the same shape as the earlier magnesium/glycine correction — **assume a supplement dose in a note is high until checked**.
  * *VILPA "40–50% lower death rates"* → Stamatakis 2022 reports **22–28%**. Inflated figures are the most common note error; check any suspiciously round large percentage.
  * *Sitting-rising test "13-year follow-up"* → Brito's median follow-up was **6.3 years**.
  * *"Apple's sleep staging is closest to lab truth"* → polysomnography validation ranks **Oura highest**, with Apple *lowest* on deep-sleep sensitivity (50.5%). A conservative-looking number can be an underestimate rather than rigour.
  * *"Less food variety → 37% more weight loss"* — **unverifiable**, and the literature partly contradicts it (restricting variety helps for energy-dense foods; *greater* variety in fruit/veg/grains predicts better outcomes). Say so in the post rather than dropping it.
* **⭐ At s2, research is where you catch the notes being wrong — and the correction is the best content in the post.** This is the Investment analogue of s1's "failed replications are content" rule, and it fired three times in the 10-08-2026 run: a note's *"every rolling 7-year period since 1926 was positive"* is false (trailing 10-year returns went negative around 1937–39 and 2008–09), and the defensible replacement is stronger — every rolling **20-year** period 1928–2005 was positive, worst 3.1%, best 17.7% (Dimensional, *The Uncommon Average*); *"99% of people have less than $10,000 in the bank"* is unsupported, and the real Fed figures are better (**63%** could cover a $400 expense, median emergency fund ~$5,000); and the ubiquitous *"missing the 10 best days halves your return"* is true but incomplete — **nine of the ten best days landed during recessions**, which turns a market-timing platitude into an argument about fear. **Correct the claim in your own voice, state plainly that the stronger version is different, and cite it.** Never silently drop a claim that failed verification — the disagreement is the most interesting paragraph on the page.
* **s3 confirmed on a second topic at scale (10-08-2026 run, 25 single-source Charisma posts):** per-post shape landed at **~460–685 words (mean ~600)** — meaningfully higher than the Investment s3 run's ~440 mean, because self-improvement notes carry more argument per note than a single financial metric does. Both sit comfortably under 800. Treat **~450–700** as the working s3 band rather than the narrower Investment figure.
* **⭐ At s3 you can still push back on a note — you just do it on *framing* rather than facts.** The documented correction rules (s1/s2) are research-driven, so it's easy to assume s3 has to take notes at face value. It doesn't. With no research available, the honest move is to name where a note's *framing* overreaches, in your own voice, and that pushback consistently made the best section of the post. Four cases from the Charisma batch:
  * A "four pillars of intimidating magnetism" note sells its habits as dominance moves → argued they work for the opposite reason (they're what someone does when they've *stopped* managing how they're received), and that running them as moves is what makes them curdle.
  * A Thomas Shelby motivational note (whose own Ark summary flags it as character-narrated fiction — **read that caveat, it's a gift**) → split "controlled" from "cold" and named the advice that doesn't survive contact with life: *never explain yourself to anyone*, and framing therapy as collapse.
  * A CIA-elicitation note → kept the technique, added a plain usability test ("would you be comfortable if they knew exactly what you were doing?").
  * A Lalo Salamanca note → kept the calm-reads-as-status observation, noted the model's natural limit given the character is a murderer.

  The rule: **a note's technique can be sound while its framing is wrong**, and separating those is available at every profile.
* **A manifest can be topically mixed, which only matters if you're synthesizing.** The 25-row Charisma CSV split cleanly into two unrelated clusters — social/psychological pieces (elicitation, social anxiety, public speaking, Machiavelli) and menswear/grooming (hairstyles, accessories, dressing like Daniel Craig). For a folder of single-source manifests this is irrelevant; every post stands alone. For a synthesized run off the whole CSV it would matter a lot, because the two clusters share no throughline and would need to become two posts. **Check cluster coherence before agreeing to synthesize a batch**, not before splitting one.
* **Duplicate-source checking can come back clean — run it anyway.** Investment was 40 notes → 34 videos and Health 25 → 23, but Charisma was **25 → 25, no duplicates at all**. The check is cheap and its result changes whether you need divergent-angle work, so it stays mandatory; just don't assume duplicates exist because the last two batches had them.
* **Investment register at s3:** keep every figure exact as the note states it (expense ratios, the 20/4/10 rule, £-denominated car comparisons, "$5,800 → $10,800"), but **attribute nothing** — state them as fact in your own voice, since s3 does no independent research to refine them. Where a note names a real study, body, or company, keep the name; where it names the creator, drop it. Second person works well here, same as the self-improvement register.
* **Word-count check gotcha:** the naive "strip frontmatter with two sed `---` passes" fails because line 1 *is* `---`. And `awk 'c==2{print} …'` has a second trap: any `---` horizontal rule *in the body* (e.g. the divider before "Sources & further reading") bumps the counter past 2 and silently truncates the count there. Use `awk 'c>=2{print} /^---$/{c++}' <file> | wc -w` to count all body words excluding frontmatter.
* **Length:** default cap is **3,000 words**, no minimum — say what the argument supports and stop; a tight ~1,800-word researched piece beat a padded 5,000-word one. If the user gives an explicit target, it overrides the cap for that run; note the override in the sign-off.
* **Output:** write to `blog-factory/output/<title-slug>/index.md` — one subfolder per post, named after the blog's own title (lowercased, spaces to hyphens, punctuation stripped), holding a single `index.md`. If that slug folder already exists, append `-2`, `-3`, etc. rather than overwrite a prior run. **`blog-factory/Archive/` holds already-published posts moved out of `output/`** (8 of them as of the 09-08-2026 run, from the Health/Habit/Charisma/Style batches), so an empty `output/` means "nothing pending", not "nothing ever produced". Check `Archive/` too when looking for prior work or a slug that's already been used. The manifest CSV appears to get removed once its post ships (`Style.csv` was deleted alongside its post being archived), so a missing CSV can just mean "already published". The `date` field (today's system date, `YYYY-MM-DD`) still goes in the frontmatter for traceability even though it's no longer part of the path. Start the file with YAML frontmatter (`title`, `topic`, `date`, and a `sources:` list of each `name` + its note's origin link) for traceability, then the post. Sign off by reporting the synthesis angle chosen, the word count, and any rows that failed to resolve.

## 🏷️ 9. NCW Adapter (Blog Post → Publish-Ready)
The last stage before publishing. The **`blog-ncw-adapter` skill** (`.claude/skills/blog-ncw-adapter/`) takes a finished `produce-blog` post and adapts it for NCW: `/blog-ncw-adapter <slug|path>`. It is pure post-processing — it never touches Ark notes or CSV manifests, and the only content it authors is the tags.
* **What the transform does**, all in place, via `scripts/adapt-post.py`: strips the `sources:` block from the frontmatter, adds `description:` (the post's first body paragraph, verbatim, YAML-double-quoted), wraps that same paragraph in the body with `{{< lead >}}` / `{{< /lead >}}`, adds a `tags:` YAML list from `--tags`, sets `date:` to a weighted-random weekday in **January–May of the current year**, and adds `draft: false`. **Each field is applied independently**, so the script is safe to re-run and safe for backfilling one missing piece (e.g. adding `tags:` to a post adapted before tagging existed).
* **⭐ `draft: false` is the correct value — adapted posts land PUBLISHED** (corrected 12-08-2026; this bullet previously said `draft: true` and that was wrong). Don't "fix" the script to write `true`, and don't pre-seed `draft: true` to hold posts back unless I explicitly ask for that on a specific batch. If a run lands on `true`, flip it with `--force-draft`. *(Hit on the 24-post Charisma batch: CLAUDE.md said `true`, the script said `false`, I asked, chose `true` — then reversed it. The reversal is the durable answer.)*
* **`draft:` is presence-checked rather than value-checked**, which is the half that still matters. Once a post carries a `draft:` line the script never rewrites it, so a value you set by hand survives any number of re-runs — **the adapter will never flip something you deliberately set**. Consequence worth knowing: pre-seeding a `draft:` value *before* the first adaptation is how you override the default, and `--force-draft` is how you overwrite one afterwards. Verified: fresh post → `draft: false` added as an unquoted YAML boolean; immediate re-run → "already fully adapted"; a hand-set value → preserved; `--force-draft` → overwritten without touching `date:`, `tags:`, or the body.
* **`date:` is *window*-checked, not presence-checked.** `produce-blog` always writes today's date, so a presence check would mean the date step never ran. A date already inside Jan–May of the current year is kept; anything else is redrawn. **Folder mode allocates weekdays deterministically** (largest-remainder, Mon→Sun weights 7…1), so the decreasing shape is guaranteed across the batch; single-post mode draws one weighted date and can't guarantee anything. Prefer folder mode for batches, and pass `--seed` to make the draw reproducible. `--force-date` redraws.
* **⭐ Tags are the *only* judgment call — everything else is mechanical.** The script has no opinion on tag content; it inserts whatever you pass. So the real work is Step 1 of the skill: **read the full body first**, then pick up to 5 tags. **Prefer the specific mechanism over the category** — confirmed good from the 09-08-2026 Investment batch: `Sequence of Returns Risk` (not "Retirement"), `Tracking Error`, `Expense Ratios`, `EV/EBITDA`, `Price-to-Book Ratio`, `Diderot Effect`, `Hedonic Treadmill`, `Veblen Goods`, `Upward Comparison`, `Sunk Cost Fallacy`. Reject the generic tier — "Investment", "Money", "Tips", "Advice", "Mindset", "Life" are all filler. **Fewer, sharper tags beat padding to 5** — 4 of the 40 posts got 4 tags because a fifth would have been noise.
* **A tag can name the post's *pushback* rather than its topic.** New from the 25-post Charisma batch: where a post's best section is the caveat it adds to its source, tagging that caveat is sharper than tagging the subject. `Conversational Ethics` on the elicitation post, `Morally Neutral Charisma` on the Lalo one, `Controlled vs Cold` and `Fictional Role Models` on the Shelby one. These read as what the post actually contributes, which a topic tag never does.
* **Topically-adjacent posts need divergent tags even when they share no source.** The dedup rule below covers same-video posts, but the Charisma batch had three *thematic* pairs/triples from entirely different videos — two Daniel Craig posts, two public-speaking posts, three composure posts. Split them the same way: wardrobe architecture (`Restricted Palette`, `Canvas Construction`) vs casual discipline (`Polo Discipline`, `Chukka Boots`); openings (`Pattern Interrupt`, `Visual Action Hook`) vs stance (`Giving Mindset`, `Story-Centric Talks`); attention-as-capital vs controlled-vs-cold vs calm-as-status. All three sets came out fully disjoint.
* **Give duplicate-source posts deliberately divergent tags.** Where the Section-8 dedup problem left several posts built on the same underlying video, identical tag sets would collide in a tag index and surface as near-duplicates. Split them on each post's actual emphasis instead — the two "waiting for a dip" posts got `Best Days` / `Loss Aversion` vs. `Opportunity Cost` / `Concentration Risk`. Some overlap between genuinely-related posts is fine and expected; a *fully* identical set is the smell.
* **A folder argument means batch — same convention as `produce-blog`.** `/blog-ncw-adapter output` doesn't name a post (there's no `blog-factory/output/index.md`); it names the container of all of them, so it means "adapt every post inside". This is now the established reading across both skills: **a directory where a single item is expected = run once per item.** The script itself is strictly per-post, so drive it from a `slug<TAB>tags` file:

  ```bash
  while IFS=$'\t' read -r slug tags; do
    [ -z "$slug" ] && continue
    python3 .claude/skills/blog-ncw-adapter/scripts/adapt-post.py "$slug" --tags "$tags" || echo "FAILED: $slug"
  done < tags.tsv
  ```

  Run it on **one post first** and eyeball the result before turning it loose on 40.
* **`blog-factory/output/` posts are untracked in git (`??`), so the `sources:` removal is not recoverable by `git checkout`.** That makes the first-post dry run the actual safety net, not git. Worth knowing before batch-adapting anything you can't regenerate.
* **PyYAML is not installed in this environment** — `import yaml` fails, so you cannot validate the result by parsing it. Verify structurally instead (this caught nothing on the 40-post run, which is the point — it's cheap):

  ```bash
  # per post: sources gone, description present & quoted, tags list 1-5, one lead pair, draft set
  grep -c '^sources:' <file>; grep -c '^description: "' <file>; grep -c '{{< lead >}}' <file>
  grep -c '^draft: false' <file>
  ```

* **Frontmatter edge cases the script already handles correctly** (all confirmed on the 40-post run — don't "fix" them): a `description:` containing `"` is escaped to `\"`; a `description:` containing `:` is safe because the whole value is double-quoted (6 of 40 had one); a tag containing `/` (`EV/EBITDA`, `EV/Revenue`) is emitted **unquoted**, which is valid YAML since `/` is not a reserved character. Tags are only quoted when they contain `:#"[]{}` or start with a YAML indicator character.
* **Second 40-post batch confirms the tag shape (10-08-2026).** Distribution landed at **33 posts with 4 tags, 7 with 5** — the "fewer, sharper beats padding to 5" rule holds up as the default rather than the exception. More mechanism-tags that earned their place: `Sequence of Returns Risk`, `Ex-Dividend Price Drop`, `Free Cash Flow Agency Costs`, `Volatility Decay`, `Tracking Error`, `NBER Dating Lag`, `Index Turnover`, `Creative Destruction`, `Veblen Goods`, `Brand Fatigue`, `Diderot Effect`, `Upward Comparison`, `Incentive Asymmetry`, `Manufactured Scarcity`, `Circle of Competence`, `Geographic Arbitrage`, `Salary Anchoring`, `Crossover Point`, `Coast FIRE`, `Tax-Gain Harvesting`. The generic tier stayed rejected.
* **Divergent tags for duplicate-source posts, worked example.** All five duplicate groups from Section 8 shipped with deliberately non-overlapping sets, split on each post's actual emphasis: the `VzjqfYEmxZ0` trio got `Maximum Drawdown`/`R-Squared`/`Bid-Ask Spread` vs `Sector Concentration`/`Market-Cap Weighting`/`Top-10 Concentration` vs `CAGR vs Annual Returns`/`Return Dispersion`/`Worst Quarter`; the all-time-high pair got `Loss Aversion`/`Regret Aversion`/`Best Days Clustering` vs `Home Country Bias`/`Equal Weight Indexing`/`MSCI ACWI`. One shared tag between related posts is fine (`Lifestyle Inflation` appeared in both $100k posts); a fully identical set is the smell.
* **One-pass structural check for a whole batch.** Faster than the per-post greps and it names the offender:

  ```bash
  for f in blog-factory/output/*/*/index.md; do
    fm=$(awk 'NR==1{next} /^---$/{exit} {print}' "$f")     # frontmatter only
    s=$(grep -c '^sources:' "$f"); d=$(grep -c '^description: "' "$f")
    l=$(grep -c '{{< lead >}}' "$f"); dr=$(grep -c '^draft: ' "$f")
    t=$(printf '%s\n' "$fm" | sed -n '/^tags:$/,$p' | grep -c '^  - ')
    { [ "$s" != 0 ] || [ "$d" != 1 ] || [ "$l" != 1 ] || [ "$dr" != 1 ] || [ "$t" -lt 1 ] || [ "$t" -gt 5 ]; } \
      && echo "PROBLEM $(basename $(dirname $f)): sources=$s desc=$d lead=$l draft=$dr tags=$t"
  done
  ```

  Expect `sources=0 desc=1 lead=1 draft=1` and 1–5 tags. Silence = all clean. Three things this version fixes, all of which produced false alarms on the 12-08-2026 run: `draft` is matched by **presence** (`'^draft: '`), so it passes on either value; the tag count is bounded to the **frontmatter** rather than `sed`-ing from `^tags:$` to `^draft:` (the script appends `tags:` *last*, so that range never terminates and runs into the body); and the glob is `*/*/index.md` because posts now live one level deeper.
* **Output is `blog-factory/output/<Topic>/<slug>/index.md` — one level deeper than it used to be.** The `produce-blog` profiles write the topic subfolder, and `adapt-post.py` handles both layouts (`_collect_posts` falls through to the nested case; a bare slug is resolved by searching one level into each topic folder). But **any `output/*/index.md` glob written for the old flat layout now silently matches nothing** — it doesn't error, it just does zero work and reports clean. `Archive/` is still flat, from before the change. Check which shape you're on before trusting a sweep that came back empty.
* **A topic folder is the natural batch unit now.** `/blog-ncw-adapter Charisma/` resolves to `output/Charisma/` and adapts every post inside; `/blog-ncw-adapter output` still does every topic in one pass. Prefer passing the explicit repo-relative path (`blog-factory/output/Charisma`) over a bare `Charisma/` — the bare form does resolve, but only after falling past a same-named candidate (`blog-factory/Charisma`, the *manifest* folder), which happens to contain no posts. Don't rely on that coincidence.
* **Whether a post has an `# H1` depends on the profile — and the "skip a leading H1" branch does fire on our own output** (corrected 10-08-2026; the earlier note here claimed it never does). `s3` posts open directly on the hook paragraph; **`s1` posts carry an `# H1` after the frontmatter**, because the s1 profile's output template specifies one. The script handles both — it skips the H1 when present and wraps the paragraph *after* it — so `description:` is always the hook rather than the title. Verified on the 25-post s1 Health batch and the 25-post s3 Charisma batch in the same `output/` directory.
* **`blog-factory/output/` accumulates across batches — scope every check by frontmatter, not by wildcard.** After the Health and Charisma runs it held 50 posts from two topics at different adaptation stages. `for f in blog-factory/output/*/index.md` then hits everything. To act on one batch, filter on the topic line first:

  ```bash
  for f in blog-factory/output/*/index.md; do
    grep -q '^topic: Charisma' "$f" || continue
    ...
  done
  ```

* **zsh does not word-split unquoted variables.** `CH="slug-a slug-b"; for s in $CH` iterates **once** with the whole string, which shows up as a bogus `MISSING FILE: <every slug on one line>` and then a division-by-zero on the count. Bash would split; this shell doesn't. Use a real array, a `while read` over a file, or — better here — select by frontmatter as above.
* **A bare `/blog-ncw-adapter` invocation doesn't always need a clarifying question.** The skill says to ask when the parameter is missing, and that's right when the answer changes the outcome. But because the script is idempotent, "adapt everything" and "adapt only what's unadapted" resolve to the *same file set* whenever every other post is already fully adapted — re-running on those is a reported no-op. Check the split first (`grep -L '^draft:'`); if the readings converge, act and say why rather than spending a round trip on a question with one possible answer.
